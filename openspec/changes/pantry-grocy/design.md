## Context

Every intake writer calls `insertIntake` in `packages/engine/src/logging/intake.ts`: `log_food`, `log_regular_meal`, the historical importer (`packages/engine/src/import/files.ts`), and `applyMealAction` in `packages/engine/src/orders/eat.ts`, which `eat_meal` and `planned_item_action` share and which inserts intake and decrements delivered meals in one SQLite transaction. The stock effect is recorded there, in the shared insert path, so a second logging service never duplicates their replay rules.

V1 serves one person. Every new personal row retains `user_id`, and the shared two-user helper tests isolation. SQL stays in query files with generated TypeSQL types. Added test lines stay at most half of added source; mutation testing is disabled.

Reuse check: npm offers Grocy MCP servers, Node-RED nodes and a Digital Alchemy integration. None fits an in-process Hono operation using Tare's existing authentication and SQLite transaction. Use Node fetch and the already-installed Zod for the fixed API calls rather than introduce a second server or automation framework.

## Goals / Non-Goals

Goals: accurate grocery stock visible to agents, confirmed eating reflected in stock, and pantry-based suggestions immediately afterward in this same change.

Non-goals: a Tare grocery scanner, automatic product creation, copying order meals into Grocy, shopping-list writes, a numerical meal solver, or automatic consumption when merely planning or suggesting food.

## Decisions

### Run a separate Grocy container

Use the maintained LinuxServer Grocy image, linked from Grocy's own README, pinned by digest during implementation. Extend the existing Compose deployment with an opt-in Grocy service, a separate persistent volume and backup/restore instructions. The reference install already runs Tare in Docker and has Compose available. Keep personal host details and installation receipts outside this public repository.

The HA add-on is supported, but its configuration uses ingress and leaves the direct web port unbound by default. An API consumer outside HA would need an explicitly exposed endpoint. Keeping Grocy beside Tare uses the existing deployment tools and avoids a Supervisor dependency. This costs a separate backup responsibility; test restoring Grocy's volume separately from Tare's SQLite backup. Do not assume the old ticket's version or port is current.

Grocy's browser interface needs HTTPS for camera scanning. Route its UI through the install's authenticated HTTPS proxy, configured to admit only the pantry owner's identity, and keep Grocy's own login enabled; another authenticated user of the proxy must not reach Grocy's UI. Keep its REST endpoint private to the engine network. Never publish its API key to the PWA. Configure `TARE_GROCY_URL`, `TARE_GROCY_API_KEY` and `TARE_GROCY_USERNAME` together, or leave all unset; a partial set prevents startup. The username names the sole pantry owner, matching how `TARE_ADMIN_USERNAME` and `TARE_SCALE_USERS` name users; it is not a new account, and startup rejects an unknown username. Only that user's operations can access the connection. Use the `GROCY-API-KEY` header, bounded requests (a fixed 30-second client deadline), no redirects and redacted errors. The settings go into `.env.example`, the configuration section of `AGENTS.md`, the `tare` service environment in `compose.example.yaml` and the environment reference in `docs/deploy.md`; `compose-example.test.ts` fails when a `TARE_` setting read in source is missing from the Compose example.

### Connection identity and reset

The engine stores the active connection as a numbered generation holding the normalized Grocy URL. Snapshot rows, bindings, recipe nutrition links and consumption requests carry that generation. At startup, a configured URL that differs from the stored one leaves the old generation in place and puts the pantry into a `reset_required` state: reads report it, refresh and dispatch stop, and nothing is sent to either server. New intake logged in this state saves nutrition and records `reset_required` as the reason stock was not updated, without creating a request. The owner can still record delivered or abandoned on old-generation requests; a not-delivered decision is refused, because no attempt could be sent. The owner-only `reset_pantry_connection` operation then cancels old-generation requests that were never claimed, clears cached stock, bindings and recipe links, and starts a new generation. It is refused while any claimed old-generation request (sending, uncertain or rejected) is unresolved. Requests are only ever dispatched to the generation they were created under, so an old product id never reaches a different server.

### Reuse Grocy's stocking tools

Grocy already provides camera scanning, purchase/consume screens and an Open Food Facts barcode lookup plugin. Use its web UI first; Barcode Buddy and companion apps remain optional clients of the same API. Tare's existing scanner continues to resolve nutrition and log food. No scan in Tare implicitly means a grocery purchase.

### Keep a stock snapshot with honest units

Read `/api/stock`, product details, product barcodes and resolved unit conversions. `/stock` is aggregate current stock, not a per-lot ledger, so the snapshot holds one row per product: amount, stock unit and the earliest best-before date Grocy reports. Per-lot detail is not stored in V1. Refresh every five minutes through the existing cron job runner, once explicitly after the runner starts (the runner has no run-on-start option), and through an explicit refresh operation. Fetch outside a database transaction, validate the whole response and replace the owner's snapshot in one transaction. Capture the connection generation before fetching and check it inside that transaction; a result fetched under an earlier generation is discarded. A valid empty response clears previous stock; a failed or malformed response preserves it with the failure reason. No partial page set is a complete refresh. A pantry that has never refreshed successfully reports `never_refreshed` and is treated as stale, never as empty.

Expose `list_pantry` and `refresh_pantry` through the operation registry, including last successful refresh, current error and whether stock is older than ten minutes. Grams are optional and require a product-specific resolved conversion; never equate one package, serving or milliliter with one gram. Pending, sending and uncertain consumption is listed beside each product rather than presented as confirmed Grocy stock. The suggestion context (below) subtracts pending and sending amounts from availability and marks a product with an uncertain request as uncertain without subtracting it, because the snapshot may already include that consume.

### Matching is an explicit binding

A binding identifies exactly one reference that intake can carry (an owned Tare food or a shared source food), one Grocy product in the active generation, that product's stock unit id at binding time, and a positive amount in that unit per Tare serving. A binding applies to the exact reference logged; there is no inheritance between a food and the source food it came from. Verify the reference is accessible and the product and unit exist. Products that use Grocy's tare-weight handling are rejected in V1, because their consume amount is a gross weight. The dispatcher reads the product immediately before each send; if it has since gained tare-weight handling or a different stock unit, the request is rejected locally with that reason and nothing is sent. A source food's barcode can propose a binding only when it resolves to exactly one product; the person or agent confirms it and the quantity. A name match never consumes stock. Reject a binding for a different product on a reference that is already bound instead of choosing one. If the product's stock unit later changes in Grocy, the binding reports a unit mismatch and consumes nothing until it is confirmed again; confirming means saving the same product for the same reference with the current unit and a quantity, which replaces the stored unit and quantity.

The binding operations are `propose_pantry_binding`, `save_pantry_binding` and `delete_pantry_binding`, available to the browser and to agents for the owner only.

For referenced intake, amount equals servings times the stored amount per serving, including the three-quarter action. Ad hoc logs with no reference have no match. A request is created only when the pantry is configured, the connection is active and the reference has a confirmed binding with a matching unit in the active generation, and only for the configured owner's intake. Otherwise no request exists, and the reason (disabled, `reset_required`, not the owner, no binding, deleted product, unit mismatch or unknown conversion) is written to the intake's pantry outcome row in the same transaction; nutrition logging still succeeds. Stock on hand is decided by Grocy, not by the snapshot: a snapshot shortage is returned as a warning and the request is still created, and Grocy's own refusal of an over-stock consume is a definite rejection. Never consume a guessed amount or silently clamp it to stock on hand. A food representing a recipe needs explicit ingredient accounting in a later change before its ingredients can be auto-consumed; V1 recipe suggestions do not claim otherwise.

### Deliver consumption without blind retries

A consumption request has its own never-reused id (`AUTOINCREMENT`), because intake ids are SQLite row ids that can be reused after the newest entry is deleted. While its intake exists, at most one request links to it per generation. `insertIntake` takes an explicit stock-effect argument: callers pass `suppress` for order meals and historical import, and every other referenced intake writes one pantry outcome row in the same `WriteScope` as the intake. That row names either the new request or the reason none was created. No HTTP happens inside a SQLite transaction. The request freezes product, unit and quantity so a later binding edit cannot change past consumption. Replaying a client id or mutation id returns the original intake and request, not a second request. Responses read the stock outcome from that row and the request's current state when they are built, so a replay shows the current state rather than a copy frozen in a stored receipt; meal receipts stored before this change have no row and report no stock outcome.

A single dispatcher claims a request transactionally, right after the intake commits and on a one-minute sweep, then sends `POST /api/stock/products/{productId}/consume`. Persist that it might have been sent before the network call. Grocy generates its transaction id server-side and has no client idempotency parameter, and stock deltas cannot prove delivery when another Grocy client also writes. Outcomes are classified as follows:

- Not sent: the pre-send product read fails, or the connection fails before any request bytes are written (refused connection, DNS or TLS failure). This is not an attempt; the request returns to pending with the error, and the next sweep tries again.
- Confirmed: a 2xx response whose body matches the expected schema. Save the returned transaction and booking identifiers and trigger a refresh.
- Rejected: a 4xx response whose Grocy error body matches the expected schema, such as not enough stock, or a local rejection after the pre-send product read. It exposes its reason and is retried only on an explicit decision.
- Uncertain: every other result once request bytes may have been written, including a timeout, a lost connection, a 3xx or 5xx response, a schema-invalid body and a restart while claimed. It is never automatically resent, because a server error does not prove there was no side effect.

Provide owner-scoped `list_pantry_requests` (unresolved, or recent resolved history with edit notices) and `reconcile_pantry_request` operations and minimal PWA controls. For an uncertain or rejected request, the person records one decision: delivered (after checking Grocy's journal), not delivered with one new attempt authorized, or abandoned (the stock effect will not be sent; nutrition stays logged). A pending request can also be abandoned. A journal check cannot rule out a request still in flight, so a not-delivered decision on an uncertain attempt is accepted only once no dispatcher holds its claim and the attempt's send time is older than a fixed 15-minute settling wait, a code constant far longer than the 30-second client deadline. The person then checks the journal. Before then the request stays uncertain. Grocy offers no verified end-to-end bound on server processing (PHP's `max_execution_time` excludes time spent in I/O on Linux), so the wait lowers the risk of a late completion but does not prove one is impossible; see Risks. Each decision carries a mutation id and the attempt number it answers. A repeated mutation id returns the first result, and a decision for an older attempt is rejected as stale, so a lost reconciliation response cannot authorize a second resend. Keep each decision and attempt in the record. A clean refresh does not resolve an uncertain request. Rollback of the intake transaction creates no request; restart never drops unresolved requests. Delivered, abandoned and cancelled requests are resolved; pending, sending, uncertain and rejected requests are unresolved.

Edits and deletions change nutrition history, not physical consumption. Before a request is claimed, a servings edit updates its frozen quantity in the same transaction, and deleting the intake cancels it. `edit_intake` cannot change the food reference; edits to the eaten-at time or note have no stock effect. Once a request is claimed or resolved, its frozen quantity never changes. A later servings edit keeps the request linked and records an edit notice; deleting the intake detaches the request with a copy of the intake's details. Neither undoes Grocy stock automatically. A delivered request stays resolved and shows the notice. A claimed or uncertain request still needs reconciliation, and a not-delivered retry sends the frozen quantity, with the notice shown beside it. This avoids treating a corrected calorie record as food returned to the cupboard.

The historical importer writes ad hoc entries with no reference, so it already has no binding; it also passes `suppress` so that adding references to imports later cannot turn old records into current pantry consumption.

### Preserve delivered-meal ownership

Delivered meal-kit meals stay Tare-only, with existing order quantity/revision rules. The order-meal branch passes `suppress` even if the nutrition food has a grocery binding. A planned grocery food follows the binding rule; a planned order meal follows the order rule. Skip never logs or consumes. Directly logging a food by reference, including through `log_regular_meal`, is a grocery-food action; agents use `eat_meal` for delivered inventory. No duplicate Grocy product is created for an order meal.

### Suggestions follow pantry delivery in this change

First add a read-only Grocy recipe adapter using `/api/recipes/{recipeId}/fulfillment` and `recipes_pos_resolved`, Grocy's per-ingredient view of resolved recipe amounts. Preserve recipe-specific units and missing quantities; do not invent a cross-unit percent-cookable number. Grocy availability is separate from nutrition. The owner links a recipe to a known Tare food and serving with `save_recipe_nutrition_link` before numerical nutrition is shown; the link carries the connection generation, and a reset clears it, so a reused recipe id on a new server never inherits old nutrition. Unknown nutrition remains unknown.

Then expose `pantry_suggestion_context` through HTTP/MCP, combining fresh grocery stock, delivered meals on hand, Grocy recipe fulfillment, known nutrition and `read_day_plan` slot budgets. Agents choose candidates from this context. Owned foods and delivered meals are planned with the existing `plan_slot`; `plan_slot` accepts only owned foods and meals, so a candidate bound through a source food is offered for direct logging with `log_food` once the person confirms. The response identifies stale stock, pending/uncertain consumption and missing nutrition. Empty pantry or no feasible candidate is an explicit result, never invented ingredients. A suggestion makes no writes and reserves no stock. For food items only (never order meals), `plan_slot` rechecks a bound food against the snapshot and returns an availability caveat when it is short, stale or uncertain; it never rejects on pantry stock. There is no claim of an optimal macro plan.

## Risks / Trade-offs

- An uncertain consume needs reconciliation. Accept this visible interruption rather than risk consuming twice; Grocy cannot atomically commit with Tare.
- A retry authorized after the settling wait can still double-consume if Grocy completes the original request even later. V1 accepts this rare case for a single owner: both bookings appear in Grocy's journal and the person reverses one there. Abandon remains the safe choice when the journal is ambiguous.
- A five-minute snapshot can miss another client's recent change. Show freshness and refresh before availability-sensitive actions; Grocy's consume response remains authoritative.
- Product-specific units need setup. Preserve the original unit and ask for a binding quantity rather than fabricate grams.
- Recipe suggestions do not yet deduct all ingredients. State that limitation in returned details and route grocery consumption through explicit food bindings only.
- A shared Grocy installation has no Tare tenant boundary. Bind it to one configured owner for V1; negative tests reject other users.
- Container storage is finite. The implementation checks space before image pulls and backs up both services; planning performs no deployment writes.

## Migration Plan

Land deployment instructions and client independently, then snapshot, bindings, delivery core, caller integration and the pantry view. Land recipe reads and suggestion context second. New migrations are additive; regenerate TypeSQL output and exercise queries against a migrated SQLite database. With Grocy configuration absent, existing logging remains usable and pantry operations report disabled.

Before enabling consumption, perform a real disposable-Grocy smoke run covering stock read, fractional consume, replay and a dropped response. Record sanitized receipts. The reference deployment is a later authorized implementation action, not part of this planning change. Disable dispatch before rolling back the engine; retain the request history and Grocy volume. Never replay unresolved work automatically after restore.
