## 1. Logging a meal from parts in grams

- [ ] 1.1 Candidate search and pick by id: `search_food_candidates` (USDA hits with a mass basis, Foundation and SR Legacy before Branded, up to 10, FDC id, name, data type, brand and kcal per 100 g, writes nothing, `lookup_unavailable` when USDA is not configured) and `add_source_food` (one record by FDC id through `fetchById` into the shared source cache, the same row on repeat), both `browser_and_agent` in access and fallback modes with MCP descriptions; tests with the `peers()` fetch fake for a generic name, a pick twice, an unknown id and a missing key; the agent operation inventory updated; no personal table, so no two-user test; builds on the existing USDA adapter (`packages/engine/src/sources/usda.ts`) and the lookup operations, no new package (complexity: standard) (gate: none)
- [ ] 1.2 Estimated amount of a referenced food: `log_food` with a food or source food reference accepts provenance `estimated` and an optional `servings_low` and `servings_high` (both or neither, low <= servings <= high), keeps the reference, sets provenance `estimated` and computes `kcal_low` and `kcal_high` from the food's per-serving kcal (or the food's own range) times the low and high servings; any other differing provenance still fails with `provenance_mismatch`; `edit_intake` on such an entry rescales the range by the ratio of new to old servings, and `amount_measured: true` restores the food's provenance and clears the range; the database range checks hold in every case; every existing logging test stays green unchanged; two-user test (a person cannot log or edit an estimated amount against another person's catalog food); builds on the intake writer, the provenance rule and `edit_intake` (`packages/engine/src/logging/`), no new package (complexity: judgment) (gate: none)
- [ ] 1.3 `log_meal_parts`: 1 to 12 parts, each with exactly one of `food_id` or `source_food_id`, grams and an optional gram range, converted with `servingsFor` against a mass basis (`dimension_mismatch` with the part's position otherwise); each part logged through the 1.2 path with provenance `estimated` and client id `<client_id>#<n>`; foods read before the transaction, then every part and its pantry stock consumption written in one `writeTransaction`, all or nothing; replay by client id returns the stored entries; the response lists the entries, the meal's totals and its summed range; per-part error detail passed through the MCP `issues` allowlist; added to `stockOperations` and the guarded paths in `packages/engine/src/pantry/egress.ts` and the agent operation inventory; an MCP smoke on a scratch database on the test box (candidate search, add by id, log two parts, read the day back) with the output in the PR body; two-user test; builds on the 1.2 writer, `servingsFor` in `packages/nutrition/src/units.ts` and `writeTransaction`, no new package (depends on: 1.1, 1.2) (complexity: judgment) (gate: none)
- [ ] 1.4 OPS (no PR): turn on USDA lookups on the reference install. The operator signs up for a free FoodData Central key; an agent sets `TARE_USDA_API_KEY` on the reference install without printing it, restarts the engine, and runs one `search_online` through MCP. Done when that search returns USDA records and the key appears in no log or file outside the install's environment. Builds on the existing USDA adapter configuration, nothing to install (complexity: mechanical) (gate: none)
- [ ] 1.5 OPS (no PR): agent photo logging procedure. A personal agent skill, kept outside this repository, reads a meal photo shared in chat, names the parts with grams and a gram range, picks a candidate for each with `search_food_candidates` and `add_source_food`, and logs the meal with `log_meal_parts`, stating each pick and the totals back to the person. Done when one real meal has been logged this way and reads back through `read_day` with a source food on every part. Builds on the 1.1 and 1.3 operations, nothing to install (depends on: 1.3, 1.4) (complexity: standard) (gate: none)

## 2. Photo estimate in the app

- [ ] 2.1 SPIKE (no PR): choose the vision model for photo estimates. Compare general vision models and dedicated food recognition APIs on food naming, gram estimation and the effect of a reference object, with published accuracy evidence, cost per photo, latency, structured output and terms for a self-hosted app where each install brings its own key. Done when a cited analysis names a primary model and a fallback and the operator accepts the choice. Builds on no package; this is research (complexity: judgment) (gate: none)
- [ ] 2.2 Photo estimate route: `POST /api/photo/estimate` mounted outside the operation registry like the inbound email route, Access or session auth, JPEG, PNG or WebP up to 5 MiB refused before any model call, the image held in memory for one call to the 2.1 model and never written to disk, the database or a log, the reply parsed with one zod schema for the slice the route reads (an invalid reply is an explicit error, never an empty list), proposed parts returned with name, search query, grams and gram range, nothing logged; provider, model and key as configuration in `config.ts`, `.env.example`, `compose.example.yaml` and `docs/deploy.md`, with 503 `vision_unavailable` when unset; tests with a fake provider for a valid reply, a malformed reply, an oversized body, a wrong content type and a missing key, and a test that no file or row is written; a live smoke with one real photo on the test box with the output in the PR body; no personal table, so no two-user test; builds on the 2.1 provider's official client or plain `fetch`, and the inbound email route's raw-body pattern (complexity: judgment) (gate: none) (depends on: 1.1, 2.1)
- [ ] 2.3 Photo tab: a fourth tab next to Scan in `apps/web/src/add-food.tsx` that captures one frame from the rear camera or takes a picked file, posts it to the 2.2 route, shows the proposed parts with editable names and grams, a candidate picker per part from `search_food_candidates` and `add_source_food`, and a Log button that calls `log_meal_parts`; hidden when the route answers `vision_unavailable`; online-only with a "Needs a connection" state and nothing queued; the photo dropped after the estimate returns; component and API tests; builds on the camera code in `apps/web/src/barcode-scan.tsx` and the existing React and TanStack Query screens, no new package (depends on: 1.3, 2.2) (complexity: standard) (gate: none)
