- [ ] 1.1 Candidate search and pick by id: `search_food_candidates` (USDA hits with a mass basis, Foundation and SR Legacy before Branded, up to 10, FDC id, name, data type, brand and kcal per 100 g, writes nothing, `lookup_unavailable` when USDA is not configured) and `add_source_food` (one record by FDC id through `fetchById` into the shared source cache, the same row on repeat), both `browser_and_agent` in access and fallback modes with MCP descriptions; tests with the `peers()` fetch fake for a generic name, a pick twice, an unknown id and a missing key; the agent operation inventory updated; no personal table, so no two-user test; builds on the existing USDA adapter (`packages/engine/src/sources/usda.ts`) and the lookup operations, no new package (complexity: standard) (gate: none)
- [ ] 1.2 Estimated amount of a referenced food: an additive migration adding `amount_estimated` (0 or 1, default 0), `servings_low` and `servings_high` to `intake_entries` with CHECKs (bounds both or neither, only on a referenced estimated row, `0 < low <= servings <= high`), the generated queries and strict intake row schema updated together; `log_food` with a reference accepts `amount_estimated: true` and an optional servings range, keeps the reference, sets provenance `estimated` and computes `kcal_low` and `kcal_high` from the food's per-serving kcal or its own range (null when kcal is unknown or no range is given); a differing requested provenance still fails with `provenance_mismatch`; `edit_intake` recomputes values and bounds from the current food on any servings or range edit, never scaling stale bounds, and `amount_measured: true` recomputes at the given or stored servings, restores the food's provenance and intrinsic range and clears the estimate; an estimated amount never consumes pantry stock and records that it did not; every existing logging test stays green unchanged; tests for the food-changed edit, an owned estimated food, a bound grocery food and the database checks; two-user test (a person cannot log or edit an estimated amount against another person's catalog food); builds on the intake writer, the provenance rule, `edit_intake` and the migration runner (`packages/engine/src/logging/`), no new package (complexity: judgment) (gate: none)
- [ ] 1.3 `log_meal_parts`: `client_id` 1 to 100 characters, optional `meal_note` up to 200, 1 to 12 parts each with exactly one of `food_id` or `source_food_id`, grams greater than 0 and an optional gram range (`0 < low <= grams <= high`); a migration adding `meal_receipts` (person, client id, normalized request hash) and `meal_receipt_parts` (receipt, position, intake entry); in one `writeTransaction` with one `eaten_at`: the receipt check (same hash returns the parts in order, different hash 409 `mutation_conflict`, a deleted member 409 `meal_part_deleted`), each food read once and used for both `servingsFor` conversion and the snapshot, each part written through the 1.2 path with `amount_estimated: true` and intake client id `meal-part:<receipt id>:<n>` (ordinary intake writes refuse that prefix), a `portion_note` labelling the original gram estimate, then the receipt and membership, no pantry stock consumed; per-part failures (missing food, volume or count basis, overflow, schema) with a stable code and position, passed through a scoped MCP `issues` allowlist; totals computed like the ledger with completeness, the meal range null when any part lacks bounds, non-finite totals refused; added to the pantry egress guarded paths and the agent operation inventory; tests over HTTP and MCP for a late-part rollback, an identical replay, a changed replay, a deleted member and a foreign food in a later part; an MCP smoke on a scratch database on the test box (candidate search, add by id, log two parts, read the day back) with the output in the PR body; two-user test; builds on the 1.2 writer, `servingsFor` in `packages/nutrition/src/units.ts`, `writeTransaction` and the `create_food` receipt pattern, no new package (depends on: 1.1, 1.2) (complexity: judgment) (gate: none)
