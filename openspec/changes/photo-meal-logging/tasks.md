## 1. Logging a meal from parts in grams

- [ ] 1.1 Candidate search and pick by id: `search_food_candidates` (USDA hits with a mass basis, Foundation and SR Legacy before Branded, up to 10, FDC id, name, data type, brand and kcal per 100 g, writes nothing, `lookup_unavailable` when USDA is not configured) and `add_source_food` (one record by FDC id through `fetchById` into the shared source cache, the same row on repeat), both `browser_and_agent` in access and fallback modes with MCP descriptions; tests with the `peers()` fetch fake for a generic name, a pick twice, an unknown id and a missing key; the agent operation inventory updated; no personal table, so no two-user test; builds on the existing USDA adapter (`packages/engine/src/sources/usda.ts`) and the lookup operations, no new package (complexity: standard) (gate: none)
- [ ] 1.2 Estimated amount of a referenced food (design D1): an additive migration adding `amount_estimated` (NOT NULL, default 0), `servings_low` and `servings_high` to `intake_entries` with NULL-safe CHECKs (the flag requires a reference, non-null servings and provenance `estimated`; bounds both or neither, only on a flagged row, `0 < low <= servings <= high`); the generated queries and intake row schema updated together, the new fields optional when decoding so stored `eat_meal` and `planned_item_action` receipts replay, with a legacy-receipt replay test; `log_food` with a reference accepts `amount_estimated: true` and an optional servings range (400 when combined with any `provenance`), keeps the reference, sets provenance `estimated`, computes `kcal_low` and `kcal_high` from the food's per-serving kcal or its own range (null when kcal is unknown or no range is given), refuses non-finite results; `edit_intake` on a flagged entry recomputes values and bounds from the current food (a new range, with or without new servings: validated against the new or stored servings; servings alone: keep the range if it still brackets, otherwise clear it; never scale stale bounds; non-finite results refused), `amount_measured: true` recomputes at the given or stored servings, restores the food's provenance and intrinsic range and clears the flag (400 with new bounds or on an unflagged entry); flagged entries take the existing pantry suppress path, so no stock request or outcome row is written; every existing logging test stays green unchanged; tests for the food-changed edit, the out-of-range edit, a range-only edit, an owned estimated food, a bound grocery food and the CHECKs; two-user test (a person cannot log or edit an estimated amount against another person's catalog food); builds on the intake writer, the provenance rule, `edit_intake` and the migration runner (`packages/engine/src/logging/`), no new package (complexity: judgment) (gate: none)
- [ ] 1.3 `log_meal_parts` (design D3): `client_id` 1 to 100 characters, optional `meal_note` up to 200, 1 to 12 parts each with exactly one of `food_id` or `source_food_id`, grams greater than 0 and an optional gram range (`0 < low <= grams <= high`); a migration adding `meal_receipts` (id, person, client id, a random UUID `part_key`, hash of the request as sent, part count; unique per person and client id), no membership table; the shared `insertIntake` refuses the `meal-part:` client id prefix for every other new write while existing rows and their retries are untouched; in one `writeTransaction` with one `eaten_at`: the receipt check (same hash returns parts `meal-part:<part_key>:1..count` in order or 409 `meal_part_deleted` if one is missing; different hash 409 `mutation_conflict`), then the receipt inserted first with a new `part_key`, each food read once and used for both `servingsFor` conversion and the snapshot, each part written through the 1.2 path with `amount_estimated: true` and client id `meal-part:<part_key>:<n>`, every insert required to report created, a `portion_note` labelling the original gram estimate, no pantry stock consumed; per-part errors `food_not_found`, `no_serving_basis`, `dimension_mismatch`, `amount_out_of_range` and `invalid_part` with a numeric one-based `part` position in the error body, identical on HTTP (through `inputRejection`) and MCP (a tool schema whose `parts` items are unconstrained so a `null` item reaches the operation's own validation); totals computed like the ledger with completeness, the meal range null when any part lacks bounds, every snapshot and total checked finite before commit (`amount_out_of_range`); added to the pantry egress guarded paths and the agent operation inventory; tests over HTTP and MCP for a late-part rollback, an identical replay, a changed replay, a deleted part, a `null` part over MCP, a pre-existing `meal-part:` intake row, an overflowing total and a foreign food in a later part; an MCP smoke on a scratch database on the test box (candidate search, add by id, log two parts, read the day back) with the output in the PR body; two-user test; builds on the 1.2 writer, `servingsFor` in `packages/nutrition/src/units.ts`, `writeTransaction` and the `create_food` receipt pattern, no new package (depends on: 1.1, 1.2) (complexity: judgment) (gate: none)

## 2. Photo estimate in the app

- [ ] 2.1 SPIKE (no PR): choose the vision model for photo estimates. Compare general vision models and dedicated food recognition APIs on food naming, gram estimation and the effect of a reference object, with published accuracy evidence, cost per photo, latency, structured output and terms for a self-hosted app where each install brings its own key. Done when a cited analysis names a primary model and a fallback and the operator accepts the choice. Builds on no package; this is research (complexity: judgment) (gate: none)
